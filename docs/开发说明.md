# 聚合图床插件：开发说明

面向维护者。用户教程见根目录 `readme.md`（会打进插件包）。

## 目录结构

```text
聚合图床/
├── plugin.json       插件元信息（打进 ZIP 根目录）
├── uploader.json     程序入口：多登录方式、权限、请求与响应规则
├── readme.md         用户教程（打进 ZIP）
├── LICENSE
├── assets/icon.png   插件图标（打进 ZIP）
├── tools/pack.ps1    打包脚本，不进入 ZIP
├── tools/check-plugin.py 安装期规则自查，不进入 ZIP
├── docs/开发说明.md   本文件，不进入 ZIP
└── releases/         打包产物，不进入 ZIP
```

ZIP 根目录必须直接是 `plugin.json` / `uploader.json` / `readme.md` / `assets/`，不能再套一层文件夹。

## 为什么合并

原来的两个插件分别是「聚合图床（账号登录版）」（`io.github.ruzmarin.picora.superbed-account`）和
「聚合图床Superbed(API)」（`io.github.ruzmarin.picora.superbed-api`），图床相同、只是鉴权方式不同。
Picora 1.1.0 起支持 `authModes`（多登录方式），同一个图床的多种鉴权可以放在一个插件里：

- 用户新建配置时先选登录方式，表单只显示当前方式的字段；
- 只校验、只发送当前方式的字段，切换方式不会把另一种方式的凭证带进请求；
- 凭证缓存按「插件 + 配置组 + 配置值 + 方式」隔离，切换方式不复用旧凭证；
- 列表里的「需认证」「Token」「账号」标签由全部方式的字段合并推导，登记文件不用填。

合并后插件 ID 为 `io.github.alnitak44.picora.superbed`，版本从 `1.0.0` 重新起算，最低 Picora 版本 `1.1.0`。
作者的署名、仓库所有者与 `LICENSE` 版权行统一为同一个 GitHub 账号，见 `plugin.json` 的 `author` / `repository`；ID 的命名空间必须是小写用户名，所以写成同一账号的小写形式。

## 程序结构（uploader.json）

```text
schemaVersion: 2
requires: auth-modes / prepare / conditional-json-fields / credential-cache / credential-refresh / response-conditions
permissions.network: www.superbed.cn（登录 + 账号上传）、api.superbed.cn（API Key 上传）
config: []                      # 两种方式没有公共字段
authModes:
├── account（账号密码）           # 默认方式（未选择时客户端取第一个）
│   ├── config: account(text, role=account) / password(secret)
│   ├── prepare.login           # POST /api/v1/auth/login，条件字段 email / username
│   │   ├── 导出 accessToken（secret）
│   │   └── cache.ttlSeconds=1800, refreshBeforeSeconds=60
│   └── upload                  # POST /api/v1/upload/，Bearer ${steps.login.accessToken}
│       └── refreshCredentials: steps=[login], statuses=[401], maxAttempts=1
└── api-key（API Key）
    ├── config: apiKey(secret, role=token)
    └── upload                  # POST https://api.superbed.cn/upload，X-API-Key
```

要点：

1. **条件字段**：账号含 `@` 发 `email`，否则发 `username`，不成立的字段完全不进请求体；
   条件只能引用文本配置，所以 `account` 必须是 `text` 而不是 `secret`，`password` 才是 `secret`。
2. **令牌缓存**：登录令牌按配置组缓存 30 分钟，提前 60 秒刷新；上传 401 时按
   `refreshCredentials` 重新登录并重试一次，第二次仍失败即停止，不重复上传图片。
3. **业务判断**：账号方式看 `success == true`；API 方式看 `err == 0`（数字零，不是字符串）。
4. **文件字段**：账号方式是 `files`，API 方式是 `file`，两者不能互换。
5. **没有 delete**：两个接口都没有可用的单图删除，程序不声明 `delete`，客户端不会显示「云删除」。

## 打包

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\tools\pack.ps1 -Force
```

默认输出 `releases/superbed-<version>.picora-plugin.zip`，并打印大小与 SHA256。
脚本会校验 `packageVersion`、`runtime` 与入口 `schemaVersion` 是否匹配、SemVer、条目数与单文件大小。

发布到插件仓库时，Release 附件名必须以 `.picora-plugin.zip` 结尾（注意是点号），
例如 `superbed-1.0.0.picora-plugin.zip`。

## 已验证与未验证

- 已用 `tools/check-plugin.py` 按 Picora `1.1.0` 的安装期校验规则逐项核对：程序字段白名单、`requires` 能力、
  配置字段与 `role`、两种方式的字段键互不冲突、前置步骤导出与模板引用、请求方法/请求体/响应路径、
  `refreshCredentials` 引用的步骤有缓存、所有请求主机都在 `permissions.network` 内。
- **未做**实机安装与真实上传验证：本机 Flutter SDK 位于 `D:\项目\A-工具`（只读），
  `flutter test` 无法写入 SDK 缓存，因此没能用 `PicoraPluginPackage.decode` 跑安装期解析。
  首次发布前建议在真机上各跑一次账号密码与 API Key 上传。
- 上传接口本身来自原两个插件（线上已收录版本），请求形态没有改动，只调整了归属方式。

## 提交到插件仓库

1. 新建独立公开仓库 `picora-plugin-superbed`（与 `plugin.json` 里 `repository` 的所有者一致），发布 Release 并上传 `.picora-plugin.zip` 附件。ID 的命名空间必须是仓库所有者的 GitHub 用户名，否则插件仓库 CI 会以「id must use the GitHub owner's io.github namespace」拒绝收录。
2. Fork `picora-plugins`，新增 `registrations/io.github.alnitak44.picora.superbed.json`：

```json
{
  "id": "io.github.alnitak44.picora.superbed",
  "releaseRepository": "Alnitak44/picora-plugin-superbed",
  "assetPrefix": "superbed-",
  "minAppVersion": "1.1.0",
  "approvedPermissions": {
    "network": ["www.superbed.cn", "api.superbed.cn"],
    "readSelectedFile": true,
    "allowInsecureHttp": false,
    "deleteUploadedFile": false
  }
}
```

`plugin.json` 的 `repository` 必须与 `releaseRepository` 指向同一个仓库根地址；
`approvedPermissions` 必须与 `uploader.json` 的 `permissions` 完全一致。
`minAppVersion` 必须是 `1.1.0`：`authModes` 在旧客户端是未知字段，会直接拒绝安装。

3. 旧的两个插件可以按「退出收录」流程删掉登记文件；已装旧插件的用户不受影响，
   但要拿到这个合并版需要重新安装。

## 维护约定

- `id`、`authModes[].id`（`account` / `api-key`）和字段键发布后不要改：
  客户端保存的 `authMode` 与配置值都按这些名字对应，改了旧配置会失效。
- 改请求、响应路径或权限时递增 `version`，并同步 `readme.md` 的错误对照表。
- 新增登录方式时在 `authModes` 里加一项，`requires` 保持 `auth-modes`，不要让字段键与现有方式重名。
- 站点接口变化时优先改现有方式内的请求，不要用新方式替代旧方式（会丢用户配置）。
